# baseline完全一致キーの脆弱性調査 — 26d③

読み取り専用。`scripts/jst-date-bypass-baseline.json`・`scripts/check-jst-date-bypass.ts`のいずれも書き換えていない。

## 1. baselineのキー構成

`scripts/check-jst-date-bypass.ts`(origin/main、234行)の`violationKey()`関数(56-89行目付近)で決定される、単一の関数:

```ts
function violationKey(v: { file: string; pattern: string; code: string }): string {
  return `${v.file}::${v.pattern}::${v.code}`;
}
```

3要素の文字列連結:
- **file**: リポジトリルートからの相対パス(例: `src/app/events/[slug]/page.tsx`)
- **pattern**: 検出パターン名。5種類の固定パターンのうち、パターン4(ローカルgetter)とパターン5(date文字列split)は正規表現の**キャプチャ結果を埋め込んだ**動的な文字列(例: `local getter .getFullYear()`, `date string split("-")`)。パターン1〜3は固定文字列。
- **code**: 該当行の**全文**(`rawLine.trim()`。行コメント除去前の生テキストをtrimしたもの)

**キー構造自体は全ファイル・全パターンで同一の1関数から生成されており、ファイルごとに異なる構造にはなっていない。**(§6の停止条件「baselineのキー構造がファイルごとに異なっていた(一様でない)」には該当しない。全99件のbaselineエントリを走査し、すべて`file`/`pattern`/`code`の3キーを持つ均一なオブジェクト形であることを確認済み。)

## 2. どの要素がリファクタで壊れるか

- **file**: ファイルの移動・リネームで直接壊れる(今回は該当例なし。全25件で同一パスに存在)。
- **pattern**: 違反の種類自体が変わらない限り安定。パターン4/5の埋め込み文字列(getter名・split区切り文字)が変わるのは「違反の種類が実際に変わった」場合のみで、これは意図した挙動。
- **code(最大の脆弱点)**: 該当行の**全文一致**。以下のいずれの変更でも別キー扱いになる:
  - 変数名・識別子名の変更(リネーム)
  - 1行の式の中身の書き換え(整形・演算子順序の変更等)
  - 1行文が複数行に分割される/その逆
  - **行の内容そのものがヘルパー呼び出しへ置き換えられて違反が完全に解消された場合**(baseline側はそのファイルのエントリごと消える)

## 3. main上(rebaseなし)での現在ヒット件数とbaseline件数の差

`git archive origin/main -- src scripts`でread-only抽出したスナップショットに対し、現行ゲートを実行:

```
[JST日付バイパス検査] OK (新規違反0件。baseline内の既知違反99件は引き続き通過)
```

**差は0件。** main自身に対してはbaselineが完全に同期している。フラジリティは「mainのHEADと、mainから分岐したまま長期間rebaseされていないブランチ」を比較したときにのみ顕在化する(26cのP-1で扱った#177がまさにこのケース)。

## 4. 25件誤検出の実例(#177スナップショットの再利用、ブランチ本体は不触)

26cのP-1で#177のブランチ内容を`git archive`でread-only抽出した既存スナップショット(`p177-gate-scan/`)を再利用し、25件の内訳を突合した結果、**2つの異なる原因**が混在していることが判明した。

### パターンA: 行内容の完全一致が崩れた(純粋なキー不一致)

`src/app/events/[slug]/page.tsx`:
- main現行(baseline登録済み): `const d = new Date(dateStr);`
- #177スナップショット(分岐時点のまま): `const target = new Date(dateStr);`

変数名が`target`→`d`にリネームされたことで、行全文が一致しなくなりbaselineから外れ、「新規」として検出された。これは指示書が想定した典型ケース。

### パターンB: mainで違反自体が完全に解消された(baselineに該当ファイルのエントリが0件)

以下6ファイルはいずれもbaseline中に**0件**(そのファイル自体が現在mainでは無違反):`src/components/EventRail.tsx`, `src/components/WeighInTool.tsx`, `src/app/sitemap.ts`, `src/components/DigestPicker.tsx`, `src/app/admin/x-preview/page.tsx`, `scripts/update-fighter-records.ts`。

現行mainのコードを確認すると、実際に`eventCountdown.ts`のヘルパー呼び出しへ置き換え済みであることを確認した:
- `EventRail.tsx`: `import { daysUntilEventJst, formatEventDateJa } from "@/lib/eventCountdown";`
- `WeighInTool.tsx`: `import { shiftDateStr } from "@/lib/eventCountdown";`
- `sitemap.ts`: `import { toJstDateStr } from "@/lib/eventCountdown";`

つまりこれらは「識別子が変わった」のではなく、「#177の分岐後にmainで本物の修正(JST日付監査、[project_jst_date_audit]メモのPR群)が入り、違反そのものが消えた」ケース。baseline側にその違反の痕跡自体が残っていないため、#177の古いスナップショット中の同一コードは無条件で「新規」判定になる。

**両パターンとも根本原因は同じ**: `code`キーがファイルの現在の1行全文に依存しており、mainとブランチのどちらかで**その行に何らかの変更が入った時点で**(リネームであれ、ヘルパー移行という実質的な修正であれ)、旧ブランチ側のコードは機械的に「新規」と誤判定される。

## 5. 対策案(最低3案。推奨は書かない)

### 案1: キーから`code`(行全文)を外し、`file::pattern`のみをキーにする

- **利点**: リファクタ耐性が最も高い。変数名変更・整形・改行位置の変更では一切崩れない。
- **欠点**: 同一ファイル・同一パターンの違反が複数行にまたがる場合、区別できず1件に潰れる。現行baseline99件中、同一`file::pattern`の組み合わせが複数行にわたる実例が複数存在する(例: `EventRail.tsx`は同一の`local getter`系パターンが1行に4パターン分出現するなど、行内複数ヒットのケースがある)。「直したはずの行がまだ検出される」「新規に増えた同種違反を見逃す」という別種の誤検出・検出漏れを生む。
- **コスト**: 低。`violationKey()`の1行修正+baseline再生成(99→file::pattern単位に集約されるため件数は減る)。

### 案2: baselineを「件数の上限」方式にする(who/whereを持たない)

- **利点**: リネーム・リファクタで内訳(どのファイルの何行目か)が変わっても、総件数さえ増えなければ通過する。キー不一致という問題そのものが構造的に起きなくなる。
- **欠点**: 「どの違反が既知でどれが新規か」を個別特定できなくなる。既存1件解消+新規1件混入が同時に起きても総件数は変わらず、ratchetの本来目的(新規混入をピンポイントで検知する)が弱まる。ファイル単位/パターン単位で上限を分けても、粒度を粗くするほど同様の問題が残る。
- **コスト**: 中。件数管理へのロジック変更(`writeBaseline`/`loadBaseline`双方)、運用ドキュメント(コメント含む)の書き直しが要る。

### 案3: rebase時にbaseline再生成を標準手順へ組み込む(運用でカバー)

- **利点**: キー構造自体(`file::pattern::code`)は変えずに済む。長寿ブランチをmainへrebase/マージする際に`--write-baseline`相当の差分レビューを必須工程にすれば、キー不一致による誤検出は「rebase直後の1回だけ」人間がレビューする形に収まる。26cで追加済みの`commit_sha`/`commit_date`はこのレビュー時に「本当に新しく書かれたコードか、baseline再生成のタイミングがズレていただけか」を切り分ける材料に使える。
- **欠点**: 強制力がない(手作業依存で実行し忘れると再発する)。CIに組み込みにくい(rebase操作自体をCIから検知するのは難しい)。長寿ブランチの数だけ、そのブランチのオーナーが個別に対応する必要がある。
- **コスト**: 低〜中。ドキュメント(CLAUDE.md等)へのチェックリスト追加のみなら低コストだが、実効性(徹底されるか)は別問題。

### 案4: 26cで追加した`commit_sha`/`commit_date`をキーの一部として突合に使う

- **利点**: 仕組み自体は既に存在する(PR-F2bで`git blame`ベースの由来情報を各baselineエントリに付与済み)。
- **欠点**: 検証の結果、**この案は根本解決にならない可能性が高い**。`commit_sha`は「その行を最後に触ったコミット」を指すものであり、リネームや意味を変えないリファクタ(セマンティクス保存の変更)でも新しいコミットが積まれれば値が変わる。つまり`code`の代わりに`commit_sha`をキーに使っても、「行の中身は変わったが違反としての意味は同じ」ケースで依然としてキーが一致しなくなり、フラジリティの解消にはならない。むしろ`code`より不安定になりうる(コード内容が全く同じでも、後から`git commit --amend`やrebaseでSHAが変わるケースがあるため)。
- **コスト**: 中。キー生成ロジックの変更に加え、`commit_sha`の再計算タイミング(baseline再生成時に都度git blameを叩く必要がある)を設計する必要がある。
