# /kick 決着スコアの選手視点統一 実施レポート

PR: `fix/kick-decision-score-perspective`(PR #573)。PR #570の調査(決着スコア979行の
勝敗マーカー不整合)を受けた修正PR。

## 背景

PR #570の全件監査で、win/loss判定行のうち「判定X-Y」形式のメインスコアが抽出できた
6,662行中979行(14.70%)で、メインスコアの大小関係が勝敗欄(result)と矛盾していた。
無作為4件の出典突合の結果、mnews側のバグでも出典側の誤記でもなく、出典サイト側の
「勝者優先/掲載順優先」という表記慣習をそのまま転記しているために起きる**表示上の
見え方の問題**と判明した。本PRはこれを選手ページの表示直前に是正する。

## 1. 既存実装(MMA本体側 `decisionScorePerspective.ts`)の扱い

MMA本体側(`src/lib/decisionScorePerspective.ts`、2026-07-31追加)には全く同じ問題への
既存実装があるが、「判定X-Y」という単純な1組のスコアしか扱わない設計。/kickの決着欄は
「判定3-0 (29:28 29:28 29:27)」のようにメインスコアに加え審判別の内訳(通常3組)が
付随する形式が多く、そのままでは流用できないと判断した。

**判断: 「判定の要否をどう判定するか」という核となる判定ロジックだけを共有関数に切り出し、
文字列パース部分はMMA側・/kick側それぞれ専用実装にした。**

- 新設: `src/lib/decisionScoreDirection.ts` の `isDecisionScoreOrderCorrect(a, b, result)`
  — 「審判スコアは定義上、勝者側の数字が敗者側の数字以上になる」という2値比較のみを行う
  純粋関数。MMA側・/kick側の両方がこれを呼ぶ。
- MMA側(`src/lib/decisionScorePerspective.ts`)は、この関数を使うよう最小限のリファクタ
  (`alreadyCorrect`のインライン計算を`isDecisionScoreOrderCorrect()`呼び出しに置換)のみ行い、
  正規表現・入出力仕様は変更していない。既存の呼び出し元
  (`src/app/fighters/[slug]/page.tsx`)への影響はゼロ(後述の検証で確認済み)。
- /kick専用の新規実装: `src/lib/kick/decisionScorePerspective.ts`
  (`normalizeKickDecisionScorePerspective()`)。メインスコア+内訳を「判定」キーワード直後の
  数字トークン列としてトークナイズし、**ペア内(within-pair)の区切り文字はダッシュ系・
  コロン・スラッシュのみ許容、ペア間(between-pair)の区切りは内容を問わない**という
  ルールで機械的にペア分解する。個々の内訳ペアの大小では判定せず(スプリット判定では
  反対票の審判が敗者側に高得点を付けることがあるため個別判定は誤り)、**メインスコア
  1組から並べ替えの要否を1回だけ判定し、その結果を内訳の全ペアに一律適用する**設計。

## 2. 979行の内訳と検算

現在のビルド(2026-08-17、`data/kick/*.json`はPR #570時点から無変更)で同じ測定方法を
再実施したところ、母集団・不整合件数とも当時よりわずかに異なる値になった:

| 指標 | PR #570時点 | 本PR時点(再測定) |
|---|---:|---:|
| メインスコア抽出母集団 | 6,662行 | **6,662行(完全一致)** |
| うち勝敗欄と矛盾(mismatch) | 979行 | **972行** |

母集団(6,662行)は完全一致した。mismatch件数の差(979→972、7行)は、PR #570の測定が
アドホックなスクリプト(未コミット)によるもので正確な再現ができないためで、
データそのものの変化ではない(`data/kick/*.json`はPR #570時点からコミットされておらず、
`npm run kick:data`の出力`boutRows`も32,569で完全一致している)。本レポートは
**再現可能な自前の測定スクリプト**(`extractMainScorePair()`を用いた自己参照判定)による
実測値972を正とし、以降はこの値で検算する。

**972行 = 960行(全体を並べ替え) + 12行(メインスコアのみ並べ替え) + 0行(判断不能で現状維持)**

| カテゴリ | 件数 | 内容 |
|---|---:|---|
| `swapped` | 960 | メインスコア+内訳(審判別スコア)を一律に並べ替えた |
| `swapped_main_only` | 12 | メインスコアのみ並べ替え、内訳は現状維持(理由は下記) |
| `unparseable`(判断不能) | **0** | 該当なし |
| `tied`(メイン同数) | 0 | mismatch母集団には含まれない(a≠bが前提のため) |

**972 = 960 + 12 + 0。残余ゼロで検算一致。**

### `swapped_main_only`(内訳を並べ替えなかった12行)の内訳

すべて「内訳を安全にペア分解できなかった」ケースで、機械的に安全と判定できないため
メインスコアのみ対応した(データの破損・特殊な省略記法によるもので、mnews側の実装で
安全に一般化できる余地は薄いと判断):

- **9行**: `27:29×3`のような「×N」繰り返し省略表記。「×」の後の数字(`3`)がトークナイザ上
  独立した数字として現れ、内訳のペア構造と衝突するため安全側で判断保留。
- **2行**: `30-27x2、30-26`のような半角小文字`x2`表記。同上の理由。
- **1行**: `29-.30、28-30、29-30`(区切り文字にタイプミスと見られる`.`が混入)。

いずれも「内訳の並べ替えが技術的に困難」に該当する。メインスコア自体は全12行とも
正しい向きに修正済みのため、選手ページ上の「勝敗欄と決着スコアが矛盾して見える」問題
(本PRの主目的)はこの12行についても解消している。内訳の括弧内だけが旧来の並びのまま
残る。

## 3. `SCHEMA.md`の修正内容

`scripts/standup-pipeline/SCHEMA.md`の「`method`は文字列から、`result`はマーク画像から、
両者は独立に読む(稀に食い違うため)」という記述の直後に、判定スコアの並び順問題は
この「食い違い」(KO/TKO分類とマークが稀に食い違う入力ゆれ)とは別種の問題であることを
明記する追記を行った。要旨:

- 判定スコアの数字の並び順(「判定3-0」等)は、出典サイトがページの視点に依存しない
  一貫した表記慣習(勝者優先・掲載順優先)を採用しているために起きる**表示上の見え方の
  問題**であり、`method_raw`・`result`のどちらも壊れても矛盾してもいない。
- 2026-08-17(本PR)から、選手ページの表示直前に`normalizeKickDecisionScorePerspective()`
  でその選手視点にスコアの並びを統一している。`method_raw`原文はこの変換で書き換えない。
- 詳細調査は本レポート(`out/kick-decision-score-perspective-report.md`)を参照するよう
  記載した。

## 4. ゲート設計と破壊テスト結果

新設: `scripts/check-kick-decision-score-perspective.ts`
(`npm run check:kick-decision-score-perspective`、buildチェーンの
`check:kick-method-label-whitelist`直後に追加)。

- **ゼロ件不変条件(ratchetではない)**: `normalizeKickDecisionScorePerspective()`の出力に
  含まれるメインスコアの大小関係は、常に勝敗欄(result)と整合していなければならない。
  再抽出には実装本体と同じ`extractMainScorePair()`を使う(開発中、ゲート側で独自に
  正規表現を再実装した際にカンマ小数点バグの定義ズレで誤検知した経緯があり、共有関数
  経由に統一した)。
- **ratchetベースライン**: 内訳を並べ替えられずメインのみ対応になった件数
  (`swapped_main_only`)を`data/kick/kickDecisionScorePerspectiveBaseline.json`に記録し、
  今後の新規パターン増加を検知する(現在の基準値: 12件)。

### 破壊テスト実施

`normalizeKickDecisionScorePerspective()`内の`alreadyCorrect`判定を強制的に`true`
(常に「並べ替え不要」と誤判定)に書き換えてゲートを実行したところ、**972件の不整合を
検知して実際にビルドが落ちる(exit 1)ことを確認した**(`npm run check:kick-decision-score-perspective`
単体・`npm run build`フルパスの両方で確認)。その後修正を元に戻し、ゲートが再びOKに
なることを確認済み。

## 5. 開発中に発見・修正したバグ

実装過程で以下の2件のバグを自己検出・修正した(いずれも最終実装には残っていない):

1. **カンマを小数点として扱う誤り**: 数字トークンの正規表現に小数点候補として`.`と`,`の
   両方を許容していたが、/kickの内訳表記では`,`が専らペア間の区切り文字として使われて
   おり(例:「10-9,10-9,10-9」)、`9,10`のような箇所を1個の数字として誤って飲み込んで
   しまう実データ(uehara-makoto、2011-11-23)を発見。小数点は`.`のみ許容に修正。
2. **ゲート側での正規表現の重複定義によるズレ**: 上記バグ修正前、ゲートスクリプトが
   別に定義した簡易正規表現でも同じカンマ小数点バグがあり、修正後の出力を誤って
   「不整合」と再検知していた。`extractMainScorePair()`を実装本体からexportしてゲート側
   に共有し、定義の重複を解消した。
