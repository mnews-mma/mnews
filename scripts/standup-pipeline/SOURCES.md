## kana（読み）の方針

読みを載せているのは Wikipedia（括弧書き）と K-1 系のみ。RISE / SHOOT BOXING / KNOCK OUT の
選手ページに読み仮名フィールドは存在しない（ローマ字表記のみ）。

- 採用元の優先順: K-1 の `hero__name-kana` → Wikipedia の括弧書き（ひらがな→カタカナ変換）
- **ローマ字からの読み生成は行っていない**。`Yuki`→ユキ/ユウキ のように長音が一意に定まらず推測になるため。
  ローマ字は同一人物判定の補助にのみ使用。
- カタカナ表記の選手名は、その表記自体を読みとして採用（推測ではないため）。
- 読みが取れなかった1,064件は `kana: null`。内訳は RISE/KO/SB のみ掲載966件、Wikipedia のみ94件、K-1 4件。

## 名寄せ（重複統合）のルール

2,704行 → 2,484人。表記ゆれを正規化（NFKC・空白/中黒/装飾引用符の除去）した上で:

1. **同一ソース内の別レコードは別人として扱う**（各団体の名簿は内部で重複排除済みのため）。
   例: K-1 が「龍翔」を2件（BLACK☆Jr / EX ARES）掲載 → 別人として保持。
2. 同名かつ所属ジムが一致 → 統合（108件）
3. 同名で所属ジムが不一致 → **フルネームの場合のみ**移籍とみなし統合（32件）。
   リングネーム1語（例: 武蔵、銀次）は別人の可能性が高いため統合しない。
4. ジム情報を持たない Wikipedia 行は、候補となる団体側グループが1つに定まる場合のみ結合（80件）。
   複数候補があるものは結合せず単独レコードとして残した（13件）。

## ④' 公式ローマ字の転写ルール

### 適用前の検証（重要）

K-1公式は**かなとローマ字の両方**を公開しているため、これを正解データとして転写ルールを検証した。

* 素朴なヘボン式転写の一致率: **217/358 = 60.6%**（4割が誤り。採用不可）
* 曖昧性のあるトークンに限ると: **55.9%**
* **曖昧性なしトークンに限ると: 27/27 = 100%**

さらに RISE / KNOCK OUT のローマ字＋既知かなでも end-to-end（語順入替を含む）で **6/6 = 100%**。
よって**曖昧性なしのトークンだけを転写する**方針を採用した。

### 曖昧と判定する条件（＝転写しない）

1. **長音の省略**: マクロン無しの `o` `u` を含むもの全て。
   公式ローマ字は長音を落とすため復元不能。実例:
   `Suzuki Shota`＝スズキ **ショウタ**（ショタではない）、`Ori Kensuke`＝**オオリ** ケンスケ、
   `Shirahata Yusei`＝シラハタ **ユウセイ**、`KOTARO`＝**コウタロウ**。
   `ō/ū/ô/û` 等マクロン付きは長音が明示されているため曖昧としない（`ー`に転写）。
2. **撥音＋母音/ヤ行**: アポストロフィ無しの `n` ＋ `[aiueoy]`。
   `KENYA` はケンヤ／ケニャ、`Kenichi` はケンイチ／ケニチのいずれとも読めるため。
3. ヘボン式で解釈できない綴り（辞書に無い音）。

促音は子音重複→`ッ`、`n`＋子音/語末→`ン`。ヘボン式・訓令式の差（`shi/si`、`tsu/tu`、`ji/zi`、`fu/hu`）は
両方受理する。

### 姓名の順序

表記名と突き合わせて実測で決定した（既知かなのレコードで検証）:

| ソース | 順序 | 検証 |

| SHOOT BOXING | ローマ字の掲載なし | 対象外 |

2トークンのローマ字を持つが表記名がリングネーム（かな漢字混じりで姓名の体をなさない）のものは、
語順入替が誤りになるため除外した（例: `ねぎ魔神 / Negi Majin` を「マジン ネギ」としてしまう）。

# 追補（2026-08-15）: K-1の大会名に曜日が混入していたバグの修正

`/kick` の選手ページを実表示で確認した際に発見。K-1の3,915boutのうち**3,880件**で、
`event` の先頭に曜日が残っていた（例: `(土)K-1 WORLD MAX 2026`）。

原因は `parse_k1_page` の日付正規表現 `(?:（.）)?` が全角括弧を前提にしていたこと。
直前で `unicodedata.normalize('NFKC', ...)` をかけているため実際には `（土）` → `(土)` と
半角化されており、この指定ではマッチしなかった。加えて `(月・祝)` のように
中身が複数文字のケースもあった。

修正: `\s*(?:[（(][^）)]{0,6}[）)])?\s*` に変更。

影響範囲は `event` フィールドのみで3,880件。他フィールドは全件一致、bout件数・解決率・
勝敗内訳はいずれも不変。SHOOT BOXING / RISE / KNOCK OUT の3ファイルはバイト単位で不変
（修正が `parse_k1_page` に閉じているため）。

  ため、他団体に比べて探索コストが高い

# 「build.py部分実行」による取りこぼしの恒久対策(2026-08-15)

## 発端

Bigbang/JKA/KROSS×OVER(旧レグ)、DEEP☆KICK/HoostCup/NJKF/NKB/RIZIN(本件)と、
「名簿(`fighters.json`)が拡大したのに一部団体を再生成し忘れる」取りこぼしが3回発生した。
真因は`build.py`が全15団体のうち9団体(PROMOS 4団体・EXTRA_ORGS 5団体)しかオーケストレーション
しておらず、残りの団体は`python3 ingest_X.py`を個別に実行しない限り再生成されない構造だった
ことにある。「`build.py`を素から一発実行すれば再現する」という受入条件(上記の各節参照)自体は
正しく機能していたが、**そもそも対象に入っていない団体のスクリプトは、この受入条件で検知できない**
という死角があった。

## 対応

DEEP☆KICK・HoostCup・NJKF・NKBは元々`build()`関数(`EXTRA_ORGS`と同じ形)を持っていたが
呼び出されていなかった。RIZIN(`ingest_rizin.py`)のみモジュールトップレベルで直接実行する形
だったため、他4団体と同じ`def build(): ... return out, ...` / `if __name__=='__main__':`の形に
機械的に抽出し直した(ロジックは一切変更していない。リファクタ前後で`bouts_rizin.json`が
バイト単位で一致することを確認済み)。

`build.py`に`FORMERLY_STANDALONE_ORGS`ループを追加し、この5団体を`EXTRA_ORGS`と同じ形で

## 恒久性についての注記

これで「団体を`build.py`のオーケストレーションに追加し忘れる」という同型のミスが将来また
起きる可能性自体は残る(新規団体を追加する際に、この2つのループのどちらにも登録し忘れれば
同じ問題が再発しうる)。ただし、既知の15団体については本対応で解消済みであり、新規団体追加時は
「`build.py`一発実行で全団体ぶんの`bouts_*.json`が生成されること」を各団体追加PRの受入条件に
含めることを推奨する。
