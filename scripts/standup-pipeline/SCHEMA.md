# bouts.json スキーマ

1レコード＝1bout。**ある選手のページに載っている1行**が1レコード。
両選手ともSB公式に選手ページがある試合は**2レコードになる**（視点が違う同じ試合）。
重複排除はしない — どちらの視点でも出典URLが異なり、片方だけが持つ情報（デビュー戦表記など）があるため。
同一試合の突合が必要なら `pair_key` を使う（後述）。

## フィールド

| フィールド | 型 | 内容 |
|---|---|---|
| `bout_id` | string | `{団体}:{選手slug}:{行番号}`。KNOCK OUTはページ送りがあるため `{団体}:{slug}:{ページ}:{行}` |
| `date` | string\|null | ISO形式 `YYYY-MM-DD`。取れなければ null |
| `event` | string | 大会名 |
| `venue` | string\|null | 会場（`東京・後楽園ホール` 形式。原文のまま） |
| `fighter_slug` | string | この行が載っている選手のSB slug（＝視点の主） |
| `fighter_name` | string | 同上の表記名 |
| `opponent_raw` | string | 相手の原文（`山田 彪太朗（シーザージム）`） |
| `opponent_name` | string | 括弧を除いた相手の表記名 |
| `opponent_affiliation` | string\|null | 括弧の中身（所属ジムまたは国名。SB側が区別していないためそのまま保持） |
| `opponent_site_slug` | string\|null | 相手が**その団体の**選手ページにリンクされている場合のslug（旧名 `opponent_sb_slug`。KNOCK OUTでも使うため改名） |
| `opponent_ref` | string\|null | `fighters.json` の人物に解決できた場合、その `name` |
| `opponent_ref_gym` | string\|null | 解決先レコードの `gym`。**同名異人があるため `name` だけでは結合キーにならない**。`fighters.json` との結合は `(opponent_ref, opponent_ref_gym)` で行う |
| `opponent_resolved` | bool | 解決可否 |
| `result` | enum | 下記 |
| `result_mark` | string\|null | 判定根拠の生データ（`mark-win` 等）。検証用に必ず残す |
| `method` | enum\|null | 決着方法。下記 |
| `method_raw` | string | 決着セルの原文（`3R 判定 ※MMA`）。**必ず原文を保持** |
| `round` | int\|null | 決着ラウンド |
| `is_extension` | bool | 延長での決着か（`延長`表記） |
| `ruleset` | enum\|null | `shootboxing` / `mma` / `ofg`。`※MMA` `※OFGマッチ` 表記から |
| `note` | string\|null | 【】内の注記（タイトルマッチ名・トーナメント回戦など） |
| `is_debut` | bool | デビュー戦表記があるか |
| `title_type` | enum\|null | タイトル戦の種別。下記。書かれていないbout・判定できないboutは null |
| `pair_key` | string | 同一試合の突合用キー（`日付|両者slugをソート`）。相手が未解決だと null |
| `source_url` | string | 出典URL（**全レコード必須**） |

## `result` — 勝敗

MMAの W/L/D/NC には寄せない。「試合が成立したか」と「勝敗」を分けて表現する。

| 値 | 意味 |
|---|---|
| `win` | 勝ち |
| `loss` | 負け |
| `draw` | 引き分け |
| `no_contest` | ノーコンテスト・無効試合（試合は行われたが結果なし） |
| `cancelled` | 試合中止・不戦（試合自体が行われていない） |
| `unknown` | マークが無く判定不能 |

**`win`/`loss` の内訳（判定勝ち・KO勝ち・延長判定勝ち）は `result` に混ぜない。**
`method` と `is_extension` で表現する。延長判定勝ちは
`result=win, method=decision, is_extension=true` となる。
SB公式データでの `延長` 表記は1件のみだが、RISE・K-1では延長が常用されるため、
第2弾以降で型を変えずに済むよう最初から分離した。

不戦勝は「勝ち」だが試合は行われていない。`result=win, method=walkover` とし、
集計時に除外できるようにする（`cancelled` にはしない。SB側が勝敗として扱っているため）。

## `method` — 決着方法

`ko` / `tko` / `decision` / `submission` / `doctor_stop` / `injury_decision` /
`walkover`(不戦) / `time_limit`(時間切れ) / `draw` / `no_contest` / `other` / `null`

`method` は決着セルの**文字列**から取る。`result` は**マーク画像**から取る。
両者は独立に読む（後述の通り、稀に食い違うため）。

## `result_mark` の判定根拠（受入条件3）

勝敗はセル内SVGのファイル名に埋まっている。出現数（2,153行）:

| mark | 件数 | 判定 |
|---|---:|---|
| `mark-win` | 867 | `win` |
| `mark-lose` | 760 | `loss` |
| `mark-ko` | 480 | **`win`**（KO/TKOでの勝ち） |
| `mark-hikiwake` | 36 | `draw` |
| `mark-nocon` | 10 | `no_contest` |

### `mark-ko` は「勝ちKO限定」— 検証済み

未検証だった「`mark-ko` がKO負けにも使われるか」を、3つの独立した検証で否定した。

**検証1: KO負けは `mark-lose` で表現されている**

決着文字列とマークのクロス集計:

| mark | KO/TKO | 判定 | その他 |
|---|---:|---:|---:|
| `mark-win` | 4 | 853 | 10 |
| `mark-ko` | **473** | 1 | 6 |
| `mark-lose` | **203** | 543 | 14 |

`mark-lose` が KO/TKO と共起する行が **203件**存在する。
もし `mark-ko` がKO決着そのものを表すなら、これらは `mark-ko` になっているはず。
→ KO負けは `mark-lose`。`mark-ko` は負けには使われない。

実例（KO負けが `mark-lose` になっている行）:
`mark-lose.svg` ＋ `1R KO` — 相手にKOされた試合。

**検証2: 両者ページに載る同一試合288組で、マークが必ず相補的**

両選手ともSB公式に選手ページがある試合288組を突合した結果:

| 選手Aのマーク | 選手Bのマーク | 組数 |
|---|---|---:|
| `mark-win` | `mark-lose` | 105 |
| `mark-lose` | `mark-win` | 105 |
| `mark-ko` | `mark-lose` | 39 |
| `mark-lose` | `mark-ko` | 39 |

**`mark-ko` が `mark-ko` や `mark-win` と対になった組はゼロ。必ず相手が `mark-lose`。**
→ `mark-ko` は一方の勝ちを表す。矛盾する組み合わせは288組中0件。

**検証3: 選手ページ冒頭の戦歴サマリーと一致**

`戦歴／14戦8勝（3KO）5敗1分` のような自己申告サマリーと行のマーク数を突合。
サマリーが読める87ページ中**74ページ**で
`mark-win + mark-ko = 勝数` かつ `mark-lose = 敗数` が成立。
さらに `mark-ko` の件数がサマリーの**KO数と一致**する（蒼士: 3KO/mark-ko=3、
荒尾祐太: 2KO/mark-ko=2、有馬伶弐: 4KO/mark-ko=4、朱里: 4KO/mark-ko=4）。
→ `mark-ko` は「勝ちのうちKO/TKOによるもの」。

不一致13ページは、サマリーが他団体を含む通算成績なのに対し表が一部の試合しか
載せていないため（例: アンディ・サワー サマリー179戦 / 表69行）。マークの意味とは無関係。

### `method` を `result_mark` から導出しない理由

`mark-win` ＋ KO/TKO表記が4件、`mark-ko` ＋ 判定表記が1件ある（SB側の入力ゆれ）。
そのため **`result` はマークから、`method` は文字列から**、独立に取る。
両者が食い違うレコードは `result_mark` と `method_raw` の両方を残してあるので後から検証できる。

## `title_type` — タイトル戦種別（既存rawの再パースのみで追加、新規クロールなし）

`ko`/`decision`のような決着方法とは別に、**そのbout自体がどんなタイトル戦だったか**を
表す。既存の10ソースのraw（SB/RISE/KNOCK OUT/K-1/RIZIN/ONE/DEEP☆KICK/NJKF/HOOST CUP/NKB）を
実測した結果、語彙が揃っていたのは次の3種のみ。**「CHAMPIONSHIP」等の大会シリーズ名だけでは
判定しない**（`bouts.classify_title_type()`に集約、`SB日本フェザー級タイトルマッチ`のような
具体的な語のみを見る）。

| 値 | 意味 | 原語彙の例 |
|---|---|---|
| `title_match` | 現王者の防衛戦（挑戦者との一戦） | タイトルマッチ／暫定タイトルマッチ |
| `vacant_title_match` | 新王者を決める一戦（王座決定戦・トーナメント） | 王座決定戦／暫定王座決定戦／王座決定トーナメント（各ラウンド） |
| `challenger_decision` | 次期挑戦者を決める一戦（タイトル戦そのものではない） | 挑戦者決定戦／次期挑戦者決定戦／挑戦者決定トーナメント（各ラウンド） |
| `null` | 記載なし、またはbout単位で判定できない | — |

複合表記（例:「NJKFライト級タイトルマッチ／WBCムエタイ日本統一ライト級挑戦者決定戦」のように
2団体の認定が1boutに同居する場合）は、文字列中で**最も早く出現したパターン**を採用する
（2団体目の認定は失われるが、`note`/`method_raw`等の原文フィールド側には残っている）。

### ソースごとの取得元と結果（実測、SOURCES.mdに詳細）

| ソース | 取得元 | 結果 |
|---|---|---|
| SHOOT BOXING | bout行の大会セル内【】注記（`note`と同じ元データ） | ○ 取得できる |
| RISE | 同上（RISE自体の興行では【】注記が一度も使われていないことを実測確認） | ✕ 常にnull（該当データなし） |
| KNOCK OUT | bout行・大会名のいずれにも記載なし（実測確認） | ✕ 常にnull |
| K-1グループ | **大会名**（`battle__place`）にのみ存在。bout行単位の情報ではない | ✕ 常にnull（下記「判定に迷った点」参照） |
| RIZIN | bout単位の`headingText`（例:「第14試合／ISKA世界フェザー級タイトルマッチ」） | ○ 取得できる |
| ONE Championship | event名に記載なし（実測確認、2件のみ） | ✕ 常にnull |
| DEEP☆KICK | bout見出し行（▼/◆直後の階級・ラウンド行） | ○ 取得できる |
| NJKF | bout見出し行（第N試合／メインイベント等に続く階級行） | ○ 取得できる |
| HOOST CUP | bout見出し`<h4>` | ○ 取得できる |
| NKB | 新サイト`box_t`・旧サイト`<h6>`（いずれもbout単位の見出し） | ○ 取得できる |

### 判定に迷った点（埋めずにnullとした実例）

* **K-1グループ**: 大会名に「〜K-1ライト級タイトルマッチ〜」「〜初代バンタム級王座決定トーナメント〜」
  のような語が入る例を確認したが、K-1公式のbout行（`<li class="battle__item">`）は
  対戦相手名と決着方法のみでラウンド・階級・タイトル種別を一切持たず、**大会名はその大会に
  出場した全選手（無関係な他階級の undercard を含む）で共有される**。よって大会名だけで
  「このbout自体がタイトル戦か」を断定すると undercard を誤ってタイトル戦扱いする恐れが
  あるため、K-1由来のbout（RISE経由でK-1大会名がたまたま載っているものを含む）は
  すべて`title_type=null`のままとした。
* **NJKF の複合表記**: `njkf2022-4th.html`に「WBCムエタイ日本統一スーパーフェザー級
  タイトルマッチ／S1ジャパンJr.ライト級王座決定戦」のように2団体の認定が1boutに同居する
  見出しが2件見つかった。最も早く出現した語（この例では`title_match`）を採用する仕様で
  処理したが、該当する具体的な2boutはいずれも名簿2,482人に解決できなかったため、
  最終的な`title_type=793`件の内訳には影響していない（実測確認済み）。

## 相手の解決ルール

1. SB選手ページへのリンクがある場合、そのslugから `fighters.json` の
   SHOOT BOXING出典レコードに引き当てる（最も確実）
2. リンクが無い場合、括弧を除いた表記名を `fighters.json` の
   名寄せ済み表記（`name` および `aliases`）と**完全一致**で照合
3. 一致しなければ `opponent_resolved=false`。生の表記名を `opponent_raw` に残す

**推測でのマッチはしない。** 表記ゆれの吸収は名簿側で名寄せ済みの範囲まで。
`fighters.json` はSB・RISE・K-1・KNOCK OUT・Wikipedia掲載選手2,484人であり、
それ以外の団体のみに出場する選手は解決できない（想定内）。

# 団体別ファイル構成（第2弾で変更）

1ファイルに全団体を入れると肥大するため、団体ごとに分割した。

| ファイル | 団体 | `bout_id` 接頭辞 |
|---|---|---|
| `bouts_sb.json` | SHOOT BOXING | `sb:` |
| `bouts_rise.json` | RISE | `rise:` |

`bouts.json` は `bouts_sb.json` にリネーム。**レコードの型・フィールド名・値は一切変更していない**
（SB側2,153boutは再生成してもバイト単位で同一）。

`source_url` のホスト名で団体は判別できるため、`promotion` フィールドは追加していない。

# RISE 取り込み時の実測メモ（第2弾）

**型の変更は不要だった。** RISE公式はSHOOT BOXINGと同じWordPressテーマ系統で、
`div.fighter-senreki` > `table` > `tr` に `td.syouhai` / `td.fightername` / `td.taikai` が並ぶ構造、
勝敗マークも同じ `mark-win` / `mark-lose` / `mark-ko` / `mark-nocon` のSVGファイル名。
既存の `result` / `method` / `is_extension` / `ruleset` でそのまま表現できた。

実装上の差異（スキーマではなくパーサ側で吸収）:

1. **日付の位置** — SBは `<span>2022.06.26 東京・後楽園ホール</span>` と `<span>` に入れるが、
   RISEは `<br>` 直後の平文。`<span>` に日付が無ければセル全体を日付の位置で分割する方式に変更した。
   SB側の出力は変わらないことを差分で確認済み。
2. **`div` のクラス** — RISEは `class="fighter-senreki p-page__content"` と追加クラスが付く。
3. **選手名の見出し** — SBは `h2.fight-title`、RISEは `h2.p-fighter__profile-name`。

データ上の差異:

4. **`opponent_sb_slug` はSB専用。** RISEは対戦相手を選手ページにリンクしていないため、
   RISE由来のboutでは常に `null` になる。RISEの相手解決は**表記名の完全一致のみ**。
5. **`延長R 判定`（延長ラウンドでの判定）がRISEには実在する。**
   この場合 `is_extension=true`、`round=null`（「延長R」は数字のラウンド番号ではないため）、
   `method=decision`。第1弾で `result` に延長を混ぜず分離しておいた設計がそのまま機能した。
   SB側では延長表記は1件のみだったが、RISEでは常用される。

# 同名異人の扱い（第3弾で追加）

`fighters.json` には**同一表記名の別人が14組・31レコード**存在する
（例: `龍翔` が4人、`武蔵` が3人）。リングネーム1語の選手で起こる。
第1弾・第2弾の相手解決は表記名の完全一致で行っていたため、これらは
**先に見つかったレコードへ決め打ちで割り当てられていた**。これを是正する。

## 追加フィールド

| フィールド | 型 | 内容 |
|---|---|---|
| `opponent_ambiguous` | bool | 表記名が複数の人物に一致し、一意に絞れなかった |
| `opponent_candidates` | array\|null | 絞れなかった場合の候補（`{name, gym, orgs}` の配列） |

`opponent_ambiguous=true` のとき `opponent_ref=null` / `opponent_resolved=false` とする。

## 「未解決に戻す」ではなく「ambiguous」を選んだ根拠

未解決（`opponent_resolved=false` のみ）に戻すと、`unresolved_opponents.json` に
「名簿に居ない選手」として混ざる。しかし実際には**名簿に居る（居すぎる）**のであって、
必要なのは選手の追加ではなく候補の判別である。両者を同じ箱に入れると
名簿拡張の作業リストが汚れる。そのため専用フラグと候補リストを持たせ、
`unresolved_opponents.json` からは除外する。

同時に `opponent_ref` は null にする。誤った人物に紐付いたまま
`opponent_resolved=true` を返すと、下流の集計が黙って誤った結合をするため。
**どちらか一方に決め打ちで割り当てることはしない。**

## 一意に絞り込む判定条件

以下の順で評価し、候補が1件に定まった場合のみ `opponent_resolved=true` とする。

1. **サイト内リンク（最優先）** — SHOOT BOXINGは対戦相手を選手ページにリンクしている。
   slugは人物ごとに一意なので、同名でも確実に判別できる。
2. **bout行の所属表記による絞り込み** — 戦績表の相手セルは
   `龍翔（BLACK☆Jr）` のように所属を併記している。この所属を候補各人の `gym` と
   照合し、**一致が1件だけ**なら確定する。照合は名簿側の名寄せと同じ正規化
   （NFKC・記号除去・`ジム`/`GYM`/`道場`/`会館`/`塾`/`TEAM` 等の語を除去）を行い、
   完全一致または一方が他方を含む場合を一致とみなす。
3. 上記で絞れないものは `opponent_ambiguous=true`。

### 所属による絞り込みで使わないもの

`フリー` / `無所属` / `free` は所属として identifying でないため、
一致しても絞り込みには使わない（別人同士が同時に「フリー」でありうる）。

### 所属が候補のどれとも一致しない場合

`opponent_ambiguous=true` として残す。**「名簿に居ない第三の同名選手」と断定しない。**
選手はジムを移籍するため（第1弾で確認済み: 金子晃大は出典団体ごとに所属が異なる）、
不一致は「別人である証拠」にはならない。

## 適用結果（SB＋RISE 4,696件の解決済みboutに対して）

| 区分 | 件数 |
|---|---:|
| 同名異人に解決されていたbout | 61 |
| 　└ サイト内リンクで確定 | 3 |
| 　└ bout行の所属で確定 | 39 |
| 　└ **絞れず `ambiguous` へ** | 19 |

`ambiguous` 19件の内訳: 所属の記載なし3件、所属が候補のどれとも一致しない5件、
所属が複数候補に一致11件。

複数候補に一致する11件はすべて `海人`（RISE/SHOOT BOXING の `TEAM F.O.D` と
KNOCK OUT の `SHOOT BOXING／TEAM FOD`）で、**同一人物が別レコードに分かれている
可能性が高い**。ただし名寄せの変更は本レグのスコープ外のため、統合はせず
`ambiguous` として残した。

# KNOCK OUT 取り込み時の実測メモ（第3弾）

**KNOCK OUT公式はSB/RISEとは別基盤（Laravel）で、HTML構造が全く異なる。**
`fighter-senreki` テーブルも `mark-*.svg` も存在しない。
ただし**既存の型はそのまま使えた**（フィールドの追加・変更なし）。

## 構造

```html
<li class="fight-log fight-log--win">        <- 勝敗はliのclassに入っている
  <div class="col mark"><span class="mark__char">◯</span></div>
  <div class="col summary">
    <div class="summary__decision">KO</div>  <- 決着方法（ラウンド番号は無い）
    <div class="resultList-detail">
      <h4><span>vs</span><a href="/fighters/{slug}">相手名</a></h4>
      <a class="event-link" href="/events/{slug}">大会名<br>2026年08月08日 会場</a>
    </div>
  </div>
</li>
```

## SB/RISEとの差異

| 項目 | SB / RISE | KNOCK OUT |
|---|---|---|
| 勝敗の在り処 | SVGファイル名 `mark-win` 等 | `<li>` のclass `fight-log--win` 等 |
| `result_mark` に入る値 | `mark-win` | `fight-log--win` |
| ラウンド番号 | あり（`3R 判定`） | **無し**（`判定` のみ）→ `round` は常に null |
| 日付表記 | `2026.08.08` | `2026年08月08日` |
| 相手へのリンク | SBのみあり / RISEは無し | **あり**（slug付き） |
| ページ送り | 無し（全boutが1ページ） | **あり**（1ページ10件、`?page=N`） |
| 掲載範囲 | 他団体戦も含む通算戦績 | **自団体（KNOCK OUT/REBELS）の試合が中心** |

`◯` / `△` / `×` の記号ではなく `<li>` のclassから勝敗を取る。
記号はフォントや空白のゆれを受けるが、classは機械可読で安定しているため。

掲載範囲の差は件数に直結する。例: 久井大夢は戦績サマリー29戦に対し表は20件、
久村舜平は40戦に対し5件。**KNOCK OUTのbout総数は所属選手の通算戦数より大幅に少なくなる。**

# K-1グループ 取り込み時の実測メモ（第4弾）

対象は k-1.co.jp 配下の K-1 WORLD GP / Krush / Krush-EX（3ブランド同一CMS、
選手ページは `/fighter/{id}` で3ブランド共通）。

## 勝敗はどこから取るか（受入条件1）

**「各行に勝敗が書かれていない」という事前情報は誤り。勝敗は行内のSVGスプライトの
フラグメント識別子に埋まっている。**大会結果ページを引く必要はなかった。

```html
<li class="battle__item">
  <svg class="battle__status">
    <use xlink:href=".../icon_sprite.svg#lose" />   <- ここに勝敗
  </svg>
  <span class="battle__result">判定</span>          <- 決着方法
  <h4 class="battle__name">vs SAHO</h4>
  <a href=".../schedule/16660" class="battle__place">2026年2月8日（日）K-1 WORLD GP 2026～...</a>
</li>
```

### フラグメントの意味と対応

| フラグメント | `result` | 根拠 |
|---|---|---|
| `#judgment` | `win` | 判定・延長判定での勝ち |
| `#ko` | `win` | KO/TKOでの勝ち |
| `#lose` | `loss` | 決着方法によらず負け |
| `#draw` | `draw` | 引き分け |
| `#exi` + `試合前` | `scheduled` | **未実施の予定試合**（戦績に計上されない） |
| `#exi` + `勝敗無し` / `無効` | `no_contest` | 勝敗無し・無効試合 |

`#judgment` と `#ko` を分けているのは決着方法の違いであって勝敗の違いではない。
`#lose` は判定負け875件・KO負け608件・TKO負け60件・延長判定負け140件をすべて含み、
**負けは決着方法によらず `#lose` に統一されている**（SBの `mark-ko` と同じ構造）。
したがって `result` はフラグメントから、`method` は `battle__result` の文字列から
独立に取る（第1弾からの方針を踏襲）。

### `scheduled` の追加

`#exi` ＋ `試合前` は**まだ行われていない試合**。戦績サマリーにも計上されていない。
`unknown`（取得失敗）とは意味が違うため `result` に `scheduled` を追加した。
SB・RISE・KNOCK OUTはこの値を生成しないため、既存3ファイルに影響はない。
集計時は `scheduled` を除外すること。

## 掲載範囲は自団体のみ

3ページ実測の結果:

| 選手 | 公式サマリー | ページ上のbout行 |
|---|---|---:|
| 璃明武 | 22戦 17勝(6KO) 5敗 0分 | 24（うち `試合前` 2） |
| 愛鷹 亮 | 35戦 22勝(10KO) 13敗 0分 | 12 |
| ソフィア・ツォラキドゥ | 5戦 3勝(0KO) 2敗 0分 | 2 |

**K-1グループ内の試合しか載らない。**サマリーは通算成績なので、
他団体での試合がある選手ほど行数が少なくなる。ページ送りは無し（全boutが1ページ）。

## 独立検証: 戦績サマリーとの突合

第1弾の `mark-ko` 検証と同じ型で、フラグメントの解釈を選手ページ冒頭の
公式サマリー（`○戦○勝(○KO)○敗○分`）と突合して検証する。

璃明武（キャリアが全てK-1グループ内）での一致例:

* 取得: `#judgment` 11 + `#ko` 6 = **win 17** / `#lose` **5** / `#draw` **0** / `#exi` 2
* サマリー: **17勝 5敗 0分**、うち **6KO**
* → 勝ち・負け・引き分けすべて一致。さらに **`#ko` の件数6がサマリーの6KOと一致**し、
  `#ko` が「KOによる勝ち」であることが裏付けられる。

他団体での試合を持つ選手はサマリー（通算）と表（K-1グループのみ）が構造的に
一致しないため、**突合はキャリアが全てK-1グループ内の選手に限って有効**。
全選手での一致率は本文（SOURCES.md）に記載する。
